# Content and computation contracts

These are requirements for the new application, carried forward from applicable Aurora Next agreements. They describe intended behavior, not an existing implementation. [SPECIFICATION.md](./SPECIFICATION.md) defines release scope and later product decisions; [CHARACTER-RULES.md](./CHARACTER-RULES.md) defines character, spell and equipment mechanics. The [representative JSON baseline](./CONTENT-EXAMPLE.md) specifies initial field shapes; the full schema, C# types, persistence keys and qualification algorithm remain open unless explicitly specified below.

## Content model and authoring

- A Content Pack belongs to one Ruleset and contains declarative Elements, their Rules and optional assets. Trusted application software supplies supported mechanics. Pack data cannot execute scripts or arbitrary code.
- A selected content-defined Character Element is the root of a build. Available content is not automatically applied. A sole available Character Element may be selected automatically.
- Elements describe game concepts and reusable benefits. A new feat, skill increase or item normally composes existing supported Rules; a genuinely new mechanic may require a trusted software extension.
- An Element has one Rules tree with individual Rules and conditional groups. Group Requirements combine with contained Rules' own Requirements. Each Rule applies once per occurrence, even if several overlapping item facts are true.
- Rules and groups have stable local identities unique across their Element's entire Rules tree. Renames, reorderings and regrouping retain identity; duplicate identities are validation errors. The owning occurrence and, where applicable, the Owned Item and Decorator Application distinguish instances of a declaration.
- Distinct granting origins create distinct Element Occurrences, each with its own benefits and ordinary decisions. Their contributions combine according to the applicable policies rather than being merged merely because their definitions match.
- Named references explicitly relate Elements. A reference does not automatically grant its target, and a display name does not imply mechanics. Required missing or unresolved references are errors.
- Availability of a definition, application of an occurrence and eligibility of a benefit are distinct. Matching a definition does not by itself apply it or establish a prerequisite.
- Modifier and other supported numeric formulas use readable, bounded strings parsed and validated into typed numeric expressions, not scripts. Requirements use structured typed conditions, not formula strings. The concrete formula vocabulary, condition variants and JSON schema remain open.
- Use the approved Aurora Next representative document's field shapes as the initial JSON baseline, adapted to this application's versioned format identifier and semantic pack versions. When implementing content loading or authoring the first pack, consult [CONTENT-EXAMPLE.md](./CONTENT-EXAMPLE.md); extend beyond it through tested slices rather than treating it as a complete schema.
- Authors describe effects, Requirements, targets and formulas rather than execution phases, priorities or a separate dependency list. A mechanic contract defines its permitted targets, facts, operations, combination and source semantics; invalid subject or target use is an authoring error.
- The affected target is distinct from subjects inspected by a Requirement. For example, an item's equipped state can gate a Rule targeting Character Strength without retargeting the Rule to the item.
- Item and ordinary Elements use the same Rule and Requirement contracts for the same operation. Ordered item-property composition remains distinct from applying Character mechanics.
- Additional Element types and named-reference conventions are content-defined; the generic core does not infer proficiency, equivalence or other mechanics from type labels, display names or numeric effects. A separate built-in Capability declaration subsystem is deferred.

### Composable Element properties

- Elements combine shared identity, descriptions and Rules with the specific properties their supported game concepts require. Use a generic composition mechanism rather than requiring every Element to carry every possible game's fields or deriving an inheritance hierarchy for every combination.
- Trusted application modules provide focused parsers, validators and typed access for supported property contracts. Callers consume the typed model rather than repeatedly interpreting raw JSON or relying on display-name conventions. A generic container does not make arbitrary fields mechanically supported: required fields, types, multiplicity, compatibility and references must be validated for each supported contract. Unsupported required contracts are explicit errors.
- Content supplies the actual game definitions and values. For example, a spell can compose level, school, casting-time, duration, range, component, ritual and concentration properties; an item can compose cost, weight and equipment properties. Properties are distinct from Rules: descriptive metadata alone does not grant a benefit, establish eligibility or execute an action.
- Registered property contracts expose explicitly supported values and facts to matching, Requirements, calculations and presentation where applicable. Access retains definition and occurrence/item context; a field's existence does not automatically make it a Character statistic. Missing required data and invalid references remain explicit issues rather than guessed values.
- Element and Character composition follow [the domain-first aggregate and Ruleset-module requirements](./SPECIFICATION.md#domain-composition-and-ruleset-modules). Domain meaning and aggregate invariants drive the model; EF Core does not dictate its composition. The selected Ruleset's initialization establishes its required Character parts without forcing unrelated games into D&D state.
- Starlights' composable aggregates are design input. Exact constituent contracts, JSON discriminators and persistence mappings remain to be designed against concrete slices. Existing inline JSON fields, such as `ability` and `sheet`, are not automatically replaced by a new serialized component array.
- Ruleset-specific movement, senses, defenses and progression such as Proficiency Bonus are declared through content using supported Rules and property contracts. The generic core does not maintain a universal D&D-specific enumeration of senses or damage types. Adding a sense with already supported semantics requires content, not a generic-core edit; genuinely new semantics require trusted software support.

### Descriptions and sheet presentation

The F01 implementation uses a versioned `starlights-content/1` subset of these
contracts. It validates local pack identities, Grants, Selections, supported
numeric Rules and the typed properties needed by the reference build. Its
sheet values support numeric literals, supported statistic names, literal text
and Element-name references; its entries support base fields and unconditional
visibility. Conditional variants, broader expressions and contextual bindings
are not implemented and are rejected rather than silently ignored. The broader
first-release requirements below remain requirements for later slices.

- An Element can provide a full description for building and detail views and multiple separately authored concise sheet entries. Each entry can have its own name/label and description, so one feature can expose several small reminders without creating separate mechanical Elements. Concise descriptions are shared by the on-screen sheet and PDF; they are not automatically summarized or truncated from the full description.
- A sheet entry uses its authored sheet label, otherwise the Element name. If no concise sheet description is provided, show only that label rather than substituting the full description. The full description remains available in the detail view.
- Each sheet entry supports two distinct presentation controls: hide the whole entry, including its label and description, or hide only its description while keeping its label. Both controls can be unconditional or conditional. They never disable Rules, create or remove mechanical occurrences, or remove calculation evidence and source inspection.
- Author full and concise descriptions in Markdown rather than HTML so homebrew authors need not know HTML. Support paragraphs, emphasis, strong emphasis, lists and links; full descriptions additionally support headings and simple tables.
- Full descriptions support explicit fenced container extensions for sidebars, warnings and rules notes. For example, `::: sidebar Optional rule` opens a titled sidebar and a standalone `:::` closes it; its body contains Markdown. This is a documented Markdown extension rather than standard Markdown.
- The application owns container styling and supplies accessible browser and PDF presentations with equivalent meaning. Content selects supported semantic containers rather than supplying CSS, arbitrary layouts or executable markup. Raw HTML, scripts, embedded frames and remote images are outside the initial description format.
- Every authored sheet-facing text field supports named `{{inline-replacements}}` in the first release: entry names, descriptions, action labels, usage labels and recovery labels, including their variant overrides. Values can be calculated numbers or typed text such as a selected option's label, an Element/item name or a recovery label. Rendering reads evaluated values rather than running a second calculation or changing mechanics. Value evaluation retains the applicable Character, occurrence, decision and originating-item context.
- Support conditional sheet-description variants in the first release as well as inline replacements. Conditions use the shared structured Requirement model rather than executable template code. A selected variant can itself contain inline replacements. Each entry has its own presentation conditions and variants; hiding one entry does not by itself hide its sibling entries.
- Resolve each entry from its base presentation fields, then process its variants in authored order. Each satisfied variant overrides only the presentation fields it explicitly provides; omitted fields retain their current values. Consequently, the last matching declaration of a field wins. This permits level-5 and level-17 thresholds to overlap intentionally. Variants can change any authored presentation text, whole-entry visibility or description-only visibility; these are presentation overrides, not mechanical execution priorities.
- If an entry's variant or hiding condition is unresolved, show a local presentation-unavailable status with an inspectable reason in both browser and PDF output. Do not silently hide that entry or present its default description as definitely correct. Unaffected entries and mechanics remain available; a presentation-only problem does not make otherwise resolved numeric calculations unresolved. Invalid content syntax and references remain validation errors.
- Entries belong to their particular Element Occurrence. Keep entries from independent occurrences separate even when names or text match, and expose enough origin information to distinguish them. Evaluate each using its own class/item/source context rather than merging it with another occurrence. Automatic consolidation is deferred.
- Sheet-description conditions and values can explicitly use Character Level or the applicable Class Level. Class context follows the particular occurrence's class Grant ancestry, not an inferred primary or highest-level class. A required class context that cannot be resolved is an explicit issue rather than a guessed class or a substitution of Character Level.
- Support unconditional and conditional hiding of sheet descriptions, including a condition such as reaching level 17. Reevaluate presentation after relevant Character changes, including changes back below the threshold. Presentation conditions do not disable mechanics, remove occurrences or recorded Choices, or hide source and calculation inspection.
- An unresolved sheet-description value displays as unavailable with an inspectable reason, never as 0 or a stale result. Without Character context, identify it as character-dependent. Invalid placeholder syntax and unknown declared-value references produce explicit validation diagnostics.
- Apply the same unavailable-value behavior to text bindings and to every other sheet-facing field. A Choice binding reads the specifically identified recorded answer, not the first matching answer or an arbitrary occurrence. An unanswered or unavailable decision is not replaced with an invented choice; its state remains explainable.
- Action, usage and recovery fields are reminders, not action execution, spending or rest commands. Displaying an action name or a maximum use count neither grants casting/usage permission nor tracks remaining uses. Where a label describes an established mechanical capacity or recovery rule, reference that result rather than introducing a competing mechanical source of truth.
- Full descriptions initially remain static source/book text, including when read in the builder's Character context. Character-aware substitutions in full descriptions are a later enhancement; do not require them for the initial release or substitute invented values into source text.
- The initial serialized presentation fields and inline-value syntax are defined below and illustrated in [CONTENT-EXAMPLE.md](./CONTENT-EXAMPLE.md). The precise Markdown dialect and container grammar, Element-link syntax, complete expression/reference vocabulary, serialized Choice and originating-item text bindings, and class-context bindings remain open. These requirements do not authorize an implementation agent to invent those contracts.

#### Initial presentation fields

- Element `description` is optional static Markdown. Element `sheet` is an optional presentation object containing `values` and `entries`. An omitted `sheet` declares no authored entries; automatic standard sheet sections remain the responsibility of their supported mechanic, not inferred prose.
- `sheet.values` maps names local to the Element to supported numeric literals, numeric-expression strings or explicitly typed text bindings. A bare string remains a numeric expression, not an ambiguous text literal. The initial text forms are `{ "kind": "text", "value": "Long Rest" }` for a literal and `{ "kind": "element-name", "target": "proof:feature:foundation" }` for a required reference to an Element's display name. Other text-reference forms require explicit supported contracts; never guess their scope from a label.
- Bind and evaluate these declarations per occurrence through shared evaluation; a value used only for presentation does not contribute to a statistic. The placeholder `{{name}}` reads the named value. Initial names match `[a-z][a-z0-9-]*`; duplicate names, malformed placeholders and unknown names are validation errors. Replacement is a single pass, formatted and escaped as text rather than interpreted as Markdown, HTML or another placeholder. Placeholder processing does not apply to static full descriptions, identities, Requirements or numeric formulas.
- `sheet.entries` is an ordered array. Each entry has a stable, Element-local unique `id`, optional plain-text templates `name`, `action`, `usage` and `recovery`, an optional Markdown `description` template, optional booleans `hidden` and `descriptionHidden`, and an optional ordered `variants` array. The omitted booleans default to false; omitted action, usage and recovery fields show no label. Entry order is presentation order within that occurrence, not mechanical evaluation order.
- Each variant has a stable `id` unique within its entry, a required structured `requirement`, and at least one of `name`, `description`, `action`, `usage`, `recovery`, `hidden` or `descriptionHidden`. It overrides only fields it supplies when satisfied. An explicit false can undo an earlier visibility override; an empty text field clears its earlier text. `hidden: true` suppresses the whole entry including all labels, regardless of `descriptionHidden`; `descriptionHidden: true` suppresses only the description, leaving the other labels available.
- Entry identity combines the Element Occurrence and entry `id`; variant and entry reordering retain their identities. Presentation edits never create additional mechanical occurrences. Entry-level fields and named values are not executable content.

### Options and matching

- Selections offer candidates from available content using a shared matching vocabulary. Requirements that query Elements use the same matching semantics but explicitly identify whether they inspect available definitions or applied occurrences; references identify their operand's origin.
- Option-specific Requirements and Element Requirements determine whether a candidate is eligible. A conditional benefit inside an otherwise eligible Element does not make the entire Element unavailable.
- A non-repeatable Element is unavailable as an additional Selection answer when already applied in the relevant scope, including through a direct Grant. Ordinary build Selections use Character-wide uniqueness; supported specialized mechanics can use meaningful scopes, such as a spell source. Independent Grants still create distinct occurrences.
- Matching checks explicit identities, types, declared patterns and named references, not inferred equivalence. Symmetric exclusion between different Elements must be declared on the relevant options or Selection.
- A candidate preview does not apply its Rules or make the current Character's calculation incomplete. Additional-choice eligibility is separate from Selection capacity and from the independent evaluation of an existing answer.
- To preview a possible replacement, evaluate against a temporary snapshot with the existing answer removed; an additional-choice preview is not a hypothetical replacement. Previewing does not mutate saved Character state.

### Selection counts and retained answers

- A Selection defaults to one answer and may declare a positive fixed count. Optional, ranged and dynamically calculated counts require their own supported contracts; their exact representation remains open.
- Report declared, recorded, remaining and excess counts separately from option eligibility. Retained ineligible or unresolved answers still count as recorded answers.
- Individually eligible answers apply while a multi-answer Selection is partially complete. An unanswered position is remaining build work, not a hypothetical effect or automatically unresolved current number.
- If restored or otherwise retained answers exceed the permitted count, preserve every answer, report the local error and suppress all benefits and descendant applications from that Selection. Do not select an arbitrary subset. Report invalid references independently; unrelated results remain available.
- New edits validate the active decision, offered candidate, prerequisites, repeatability, count and numeric range before mutation. Previously accepted answers that become invalid or dormant remain stored and are revalidated when their context changes.
- Purely descriptive embedded list choices, such as prompted personality suggestions, are deferred. Optional free-form character details remain supported. If an initial-release mechanic requires a non-Element answer, such as a selected damage type, support that decision rather than presenting it as flavor or silently omitting its effects.
- Mechanically meaningful non-Element options require stable option identities, typed answer values and explicit mappings to their effects and presentation labels. Reuse normal decision identity, eligibility, capacity, retention and validation behavior. A label alone is not a mechanical identity. The precise serialized option and answer contracts remain open until the corresponding supported mechanic is specified.

### Character Options

- The selected Character Element offers Character Options as Rule Elements in named groups; catalogue availability alone neither offers nor activates an option. Offers are unconditional initially, while Rules within offered Elements can have normal Requirements.
- Group and offer identities are stable and independent of display names, order and group membership. Duplicate offers or groups, invalid targets and multiple offers of the same Rule Element are resolution errors.
- Display order is presentation only. Group membership does not itself impose a selection count, exclusivity or Rule execution order.
- An explicit player toggle overrides the offer's default, which overrides the Rule Element's default; an omitted Element default is disabled. Clearing a player override resumes the applicable content default.
- Enabling an option applies its Rule Element through the Character Element's build tree. Disabling it removes that option's origin, retains dependent answers and revalidates them if the option returns. An independently granted occurrence remains active.
- Cross-pack contributions to option groups must explicitly identify their target and obey the resolved Content Set's access and conflict rules. Conditional offers, declaration replacement and a destructive disable-and-discard operation are deferred.

## Compilation, evaluation and projection

The application composes compatible contracts for three semantic stages:

1. **Compile:** validate the resolved Content Set into reusable typed definitions, independent of individual Character edits.
2. **Evaluate:** bind those definitions to a Character snapshot, recorded answers and physical item identities; resolve dynamic Grants, eligibility, numeric dependencies and evidence.
3. **Project:** organize established results into a Character Sheet. Projection does not reevaluate Requirements, reapply effects or manufacture missing mechanics.

These stages describe responsibilities, not prescribed class names or APIs. Callers use a coherent evaluation boundary rather than orchestrating internal expansion, equipment and statistics passes.

- Validate pack-local structure, then Content Set references, supported extensions and contract compatibility, then Character-dependent eligibility and dynamic cycles during evaluation.
- A blocking compilation error rejects that snapshot with structured errors and no valid compiled model. Do not evaluate silently pruned definitions. A previously valid preview, if shown, must identify the earlier snapshot.
- An authoring tool may preserve incomplete or invalid draft data, including unsupported payloads and unrecognized fields, without presenting it as valid runtime content. A partial-draft evaluation mode and editor implementation are deferred.
- Collect independently discoverable errors in each validation stage. Skip checks whose prerequisites cannot be decoded rather than producing cascading invented errors; continue validating unrelated declarations.
- Unexpected implementation exceptions remain explicit failures rather than successful validation or evaluation results.
- Diagnostic facts include a machine-readable code, severity, message and appropriate primary location, with related locations and affected occurrence or item identities where relevant. Locations may use pack, Element, Rule/group and field identities or document paths for malformed input. Do not invent missing identities or require consumers to parse prose.
- Evaluation returns structured application outcomes, Requirement observations, contribution evidence, origins and completeness; rendered messages derive from those facts. The entire internal dependency graph need not be public.
- Known inactive benefits and unavailable unselected options are explainable normal outcomes, not automatically Character errors. An invalid recorded answer is actionable; unresolved dependencies and structural failures are explicit issues. Candidate-only preview failures remain local to the candidate.
- Registration of a supported mechanic keeps loading, validation, compilation and interpretation consistent. Independent validators accumulate; exclusive calculation or convention slots require one selected implementation unless replacement is explicit. Unsupported Rulesets, declarations, incompatible contracts and ambiguous exclusive registrations are errors, never implicit D&D fallback.
- Application composition may reuse or replace compatible stages and focused implementations. Arbitrary runtime pipeline injection and executable pack extensions are deferred.

## Requirements and independent qualification

- A Requirement evaluates to satisfied, not satisfied or unresolved. Negating unresolved remains unresolved. A known false member settles an `all` condition; a known true member settles an `any` condition. Retain relevant diagnostics even when another member settles the condition.
- Element, option, group and individual Rule Requirements gate only their declared scope. A failed benefit does not delete possessions or disable unrelated benefits sharing an Element or item.
- Evaluate a conditional decision against independent evidence excluding its own conditional outputs and their dependent Grant paths. Independent unconditional contributions, including those from the same occurrence or physical item, may qualify it.
- Retain all candidates and their origins, including suppressed and tied contributions. Recombine surviving independent candidates under their declared policy for qualification; do not subtract a contribution from an already flattened final total.
- An explicit mutually exclusive alternative evaluates its condition in one independent view excluding every branch's outputs and dependents. For “Expertise if independently proficient, otherwise Proficiency,” known proficiency selects Expertise, known absence selects Proficiency, and unresolved evidence selects neither and reports the unresolved decision. Exact alternative syntax remains open.
- Applied membership queries use independently qualified occurrences, not catalogue presence or hypothetical unchosen options. A chosen answer cannot disqualify itself merely by producing the fact its negative Requirement checks.
- Requirement evaluation and numeric formulas have different semantics. A formula reading the final value it defines is a cycle, not an implicit previous partial value or an independent qualification view.
- When optional item-benefit activation is introduced, its intent must be specific to the item and named optional benefit. Disabling it does not unequip or unattune the item, suppress unrelated mandatory effects or curses, or remove costs. Enabling it does not satisfy other Requirements. Activation commands and detailed curse state are deferred.
- When item-set conditions are supported, count distinct qualifying physical items rather than occurrences or Grant paths. The detailed set-state and query contracts remain open.

## Dependencies, occurrences and cycles

- Derive value reads and output dependencies from parsed formulas, Requirements and mechanic contracts. Compilation records dependency templates; evaluation binds instance-level dependencies as occurrences and query matches become known.
- A Rule without a Requirement can still wait for numeric dependencies. Waiting, a known unmet Requirement and an unresolvable dependency are different outcomes. Do not rely on blind retries, discovery order or author-supplied phases to produce a correct result.
- Qualification views and final-value views are distinct. Once independently qualified, a conditional contribution may affect the final value. Any reuse of a qualified result must respect its exclusion scope.
- An occurrence identity follows its parent occurrence and stable Grant identity, or its owning occurrence, Selection identity, answer identity and selected Element. Item ancestry retains the particular Owned Item and Decorator Application.
- Re-evaluating an origin does not create another occurrence. Removing or reordering another origin does not renumber survivors. Replacing a selected Element does not attach its former child answers to the replacement; the original answers can return when the original Element is selected again through the same decision.
- A granted child's eligibility depends on its particular Grant and retains originating-item context when applicable. Missing required item binding is an explicit error, not a guessed item or a false Requirement.
- Independent repeated occurrences are valid. Recursive occurrence creation along an active Grant chain is not: reject statically evident unconditional recursion during validation, and report Character-dependent recursion with the affected Element and Rule chain during evaluation. Qualification or numeric dependency cycles are distinct diagnostics.
- Unresolved potentially relevant contributions make affected results unavailable or incomplete, with known contributions and reasons retained. Dependent results inherit unresolved status; independent results continue. Do not present a known subtotal as a final value.

## Numeric composition and abilities

- Supported mechanics own their permitted operations and combination policies. An ungrouped increase adds once per eligible occurrence. For the initial generic grouped policy, take the greatest signed eligible value in each Stacking Identifier and add the group results. Thus +2 and +3 in one group plus +1 in another yields +4; -2 and -5 in one group yields -2, not zero. Retain suppressed and tied sources.
- Group labels cannot turn incompatible armor formulas into additive bonuses or bypass a named training mechanic's policy. A worst-penalty policy or additional operation needs an explicitly supported contract.
- Content defines the abilities, checks, explicit formulas and contribution values available to a Character. Identical declarations of one shared named subject do not repeat its base formula; incompatible definitions for the same subject are reported.
- A Ruleset-owned, validated ability-prefix convention binds each content-defined Ability to its supported input, increase, setting, maximum, effective-score and modifier roles. The generic core does not hardcode D&D ability names. Display names and abbreviations do not determine the binding. Exact suffixes and serialized bindings remain open.
- The selected Ruleset composes resolved input, ordinary increases, eligible setting candidates and the applicable maximum. For 5e5, calculate the ordinary score, compare it with the eligible setting result if present, then apply the maximum. Competing setters for one Ability use the Ruleset's shared highest-wins group; a conflicting authored group is rejected.
- Resolve an absent Ability Score Input from the Ability Element's declared default, otherwise 0. An explicitly recorded 0 remains the input. Identify fallback-derived values and report missing required decisions; invalid recorded inputs and unresolved contributions are not treated as absent.
- Preserve the recorded input, ordinary pre-limit value, maximum, eligible and suppressed contributions, effective score and their origins. Modifiers and other consumers read the effective score. Raising a maximum can reveal previously limited contributions without changing the saved input.
- The ability calculator receives resolved inputs rather than scanning Character state, inventory or Requirements. Shared evaluation owns eligibility, readiness and incomplete-result propagation.
- Check availability is distinct from Proficiency and Expertise. Training is represented by explicit Elements and declared policies, not inferred from a label or bonus. Multiple sources can establish one check without duplicating its base formula.
- Unrelated numeric properties may be unknown rather than zero. Where item cost, value or weight is supported, preserve the distinction between an omitted amount and an explicitly declared zero; supported stack totals and ordered property replacements retain source evidence.
